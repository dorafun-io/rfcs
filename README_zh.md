# DoraFun RFCs (技术提议请求)

“RFC”（请求意见稿）流程旨在为 **DoraFun** 生态系统（包括 `dop` 命令行运行时、DoraFun 平台、以及具身智能硬件与通信协议）的重大变更提供一条一致且受控的路径，以确保所有利益相关方对项目的演进方向充满信心。

许多常规变更，包括错误修复（Bug fixes）和文档改进，均可通过常规的 GitHub Pull Request 工作流在各自的代码仓库中直接实施与审查。

然而，某些变更是“实质性”的。我们要求这些变更必须经历一定的设计讨论流程，以在 LoopFun 开源社区、核心维护者以及商业合作伙伴（如 DoraOne）之间达成共识。

## 何时需要遵循此流程

如果你打算对 `dop`、DoraFun 平台或 RFC 流程本身进行“实质性”变更，你必须遵循此流程。“实质性”变更的界定取决于你提议更改的生态模块，但通常包括以下内容：

- 对 `dop` CLI 命令、语法或参数的任何语义层面的更改。
- 对 DORA 零拷贝共享内存总线或 Zenoh 网络拓扑的破坏性架构调整。
- 制定新的硬件接口标准（例如针对昇腾 CANN、ARM 等异构架构的适配标准）。
- 对 DoraFun 包管理流转、节点集市或部署流程的重大基础性新增。

部分变更无需通过 RFC 流程：
- 重新措辞、重组、重构或其他“改变形态但不改变含义”的工作。
- 严格改善客观质量指标的新增内容（如性能提速、消除警告、增加平台测试覆盖率）。
- 仅对核心开发者可见，但对 `dorafun-io` 最终用户不可见的微小错误修复或基础设施更新。

如果你直接向 `dorafun-io/dop` 提交包含重大新功能的 Pull Request 而未经过 RFC 流程，该 PR 可能会被礼貌地关闭，并提示你先提交一份 RFC。

## 创建 RFC 之前

仓促提交的 RFC 可能会降低其被接受的概率。质量低下的提案、针对之前已被否决功能的提案、或与近期路线图不符的提案，可能会被迅速拒绝。

在撰写 RFC 之前，去寻求其他核心开发者的反馈通常是个好主意。最常见的准备工作包括在 **LoopFun 社区论坛** 或 GitHub Discussions 中探讨该想法，或偶尔发布“前置 RFC (Pre-RFCs)”。如果能从资深开发者那里获得鼓励性反馈，这通常是该 RFC 值得推进的良好信号。

## 具体流程说明

简而言之，要将一项重大功能加入 DoraFun 生态，首先必须将对应的 RFC 作为 Markdown 文件合并到本仓库中。至此，该 RFC 即变为“活跃 (Active)”状态，并准备好进入代码实施阶段。

1. **Fork** 本 RFC 仓库 (`dorafun-io/rfcs`)。
2. **复制** `text/0000-template.md` 并重命名为 `text/0000-my-feature.md`（“my-feature”应具描述性）。此时请勿分配 RFC 编号。
3. **充实 RFC 内容**。请注重技术细节：如果 RFC 缺乏令人信服的动机、未能展现对边缘硬件影响的深刻理解、或对缺点避而不谈，往往会遭到冷遇。
4. **提交 Pull Request**。RFC 将通过 PR 接受广大社区的设计反馈。
5. **更新编号**：PR 开启后，请使用该 PR 的议题编号重命名文件（例如，将 `0000-` 前缀更新为实际的 PR 编号）。
6. **建立共识**并整合反馈。你可以将大大小小的修改作为新的 commit 推送到该 PR。**请特别注意：一旦 commits 在 PR 中可见，请勿进行 squash 或 rebase 操作。**
7. **最后征求意见期 (FCP)**：在充分讨论后，核心团队成员将发起“进入最后征求意见期 (FCP)”的动议，并附带对该 RFC 的*处置意向*（合并、关闭或推迟）。FCP 为期 **7 个自然日**。这确保了所有利益相关方在最终决议下达前，均有充足的时间提出最后的异议。

## RFC 生命周期

一旦 RFC 变为“活跃”状态，作者即可开始编写代码，并将功能作为 Pull Request 提交至相应的 `dorafun-io` 仓库（如 `dorafun-io/dop`）。“活跃”状态并非橡皮图章，但它意味着原则上所有主要利益相关方已对该功能的设计达成了一致。

此外，RFC 被接受并不意味着实施该功能的优先级，也不代表其他核心开发者有义务去实现它。虽然并非*必须*由 RFC 作者亲自实现，但这通常是将 RFC 推进到最终完成的最有效方式。

## 审查 RFC

核心团队在充分理解了提案的收益与代价后，将做出最终决议。决议做出后，RFC 的 PR 将被合并或关闭。团队会在评论区留下描述决策合理性的说明。

## 实施 RFC

每一个被接受的 RFC 都将在相关的代码仓库（如 `dorafun-io/dop` 或 `dorafun-io/platform`）中拥有一个关联的“追踪任务 (Tracking Issue)”。RFC 作者不必强制实现它，但非常欢迎作者在 RFC 被接受后提交实施方案以供审查。
